## Назначение
Облако сохранений раньше использовало Supabase-проект автора. Сейчас приложение не хранит сейвы на собственном сервере: пользователь подключает папку, которую синхронизирует desktop-клиент, WebDAV или ранее настроенное поддерживаемое хранилище. Ручные формы для ввода S3 и Supabase infrastructure credentials убраны из пользовательских настроек; существующие S3 и разрешённые Supabase-подключения можно восстановить через connection card или обработать в main-процессе. Встроенный вход по email/паролю удалён вместе с зависимостью `@supabase/supabase-js`.

## Для пользователя
**Первый запуск.** В мастере появился шаг «Saves»: приложение само находит клиенты облаков на ПК (OneDrive, Dropbox, Google Drive, Яндекс.Диск, iCloud, MEGA, pCloud, Nextcloud, ownCloud, Box, Proton Drive, Sync.com, Mail.ru Cloud) и показывает карточки «Use this cloud». Один клик — папка `<облако>\F95Launcher Saves` создана, подключена, первая синхронизация запущена. Кнопки «Choose another folder…» (любая папка, которую синхронизирует клиент) и «I have a connection card…» (восстановление на новом ПК). «Keep saves on this PC» — пропустить.

**Settings → Save storage.** То же самое плюс:
- **WebDAV server** — адрес, логин, пароль приложения (Nextcloud, ownCloud, Яндекс.Диск `https://webdav.yandex.ru`, Box, pCloud, Koofr, NAS). **Test connection** показывает, найдено ли в этом месте хранилище с другого ПК и зашифровано ли оно.
- **Protect saves with a passphrase** — шифрование каждого объекта (AES-256-GCM, ключ из scrypt). Фраза нужна на каждом ПК; восстановить её нельзя.
- После подключения: статус, последняя синхронизация, ошибки, **Sync now**, **Export connection card…** (файл `.f95card`, при желании запечатанный отдельной фразой — тогда его можно пересылать), **Disconnect…** (данные в хранилище остаются).
- **Backups in this storage** — каталог всех игр с бэкапами с любого ПК: что уже в библиотеке, что ещё не установлено; **Restore** для установленных.

Ручных полей для S3 или Supabase здесь нет. Если уже настроенное подключение поддерживается, его можно перенести карточкой подключения. Для Supabase принимаются только publishable key (`sb_publishable_…`) или legacy `anon` JWT с ролью `anon`; `sb_secret_…` и `service_role` отклоняются. Бакет должен быть создан заранее и иметь политики Storage для разрешённой роли: приложение не создаёт бакеты и не вызывает bucket-admin API. Этот провайдер не устанавливает Supabase Auth-сессию: API key идентифицирует приложение, а без пользовательской сессии Storage-запросы выполняются как `anon`. Поэтому это не user-scoped sync и не даёт изоляции между отдельными пользователями. См. [официальное описание Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys).

**Панель игры → Saves.** Если хранилище подключено: «Back up to OneDrive», «Restore from OneDrive»; иначе одна кнопка «Connect your cloud», которая ведёт в настройки. Локальные функции (экспорт/импорт файла, vault) не зависят от хранилища.

**Повторное подключение на другом ПК.** Используйте тот же desktop-клиент и карточку «Use this cloud» для уже синхронизированной папки либо импортируйте `.f95card` с ранее настроенными параметрами соединения. Если хранилище зашифровано, приложение просит фразу до любых изменений; неверная фраза ничего не трогает.

**Автоматика.** Сверка всех установленных игр через 20 с после запуска, после установки/обновления игры, после подключения/разблокировки, и после игры: при запуске игры папки сохранений берутся под наблюдение, изменение + 90 с тишины → сверка и выгрузка. Если найдено только локальное или только удалённое содержимое, используется эта сторона. При двух разных копиях baseline последней синхронизации определяет, изменилась ли только одна сторона; если обе стороны считаются изменёнными (в том числе до первой синхронизации, когда baseline-хеши отсутствуют), приложение показывает конфликт и ждёт явного **Back up** или **Restore**. Время файлов не выбирает победителя. Перед импортом и восстановлением текущие сохранения сначала копируются в локальный vault; при ошибке резервирования операция прекращается.

## Как это работает
1. **Провайдеры** (`providers.js`): один интерфейс `list/read/write/remove/test` над плоскими posix-путями. `folder` — атомарная запись через временный файл и rename (клиент облака никогда не увидит полузаписанный архив). `webdav` — PROPFIND Depth 1 рекурсивно, MKCOL родителей при 404/409 на PUT, Basic auth, разбор multistatus без XML-зависимости, коды `auth_failed` (401/403), `disk_full` (507). `s3` — SigV4 без AWS SDK: ListObjectsV2 с пагинацией, Get/Put/DeleteObject, path-style по умолчанию (R2, B2, MinIO).
2. **Автоопределение** (`cloudFolderDetector.js`): переменные `OneDrive*`, `Dropbox\info.json`, буквы дисков с `My Drive` (Google Drive for desktop), `P:\pCloud Drive`, типовые папки в профиле. Каждому предлагается подпапка `F95Launcher Saves`.
3. **Настройки** (`storageConfig.js`): соединение хранится в конфигурации приложения, секреты и фраза шифрования — отдельно через `safeStorage` (DPAPI на Windows); если ОС не предоставляет `safeStorage`, статус показывает предупреждение. Активно одно подключение: `connect` заменяет его, `disconnect` стирает локальную конфигурацию, не удаляя удалённые файлы. Карточка подключения — JSON с `format: "f95launcher-save-storage"`, при фразе — AES-256-GCM + scrypt. При ошибке атомарной записи конфигурации предыдущий файл сохраняется.
4. **Раскладка в хранилище** (`saveStorageSync.js`): `storage.json` (маркер: формат, шифрование, соль, контрольное значение, кто создал), `catalog.json` (все игры с бэкапами), `games/<identity>/latest.zip`, `latest.manifest.json`, `history/<ts>.zip` (последние 5). Для WebDAV всё лежит в подпапке `F95Launcher Saves`, для S3 — под `prefix`. `identity` = `f95-<id темы>` (тот же, что у vault и старого облака).
5. **Архив** — формат файлового экспорта (см. save-transfer.md): `exportGameSavesToFile` для выгрузки, `importGameSavesFromFile` для восстановления (сопоставление профилей по стратегии/провайдеру, поэтому разные папки AppData на двух ПК не мешают).
6. **Решение** — общий `decideSaveSyncPlan`. Одинаковое содержимое считается синхронизированным независимо от mtime. При различиях сохранённые хеши последней синхронизации позволяют распознать, что изменилась только одна сторона; если обе стороны считаются изменёнными (включая случай, когда оба baseline-хеша отсутствуют), получается конфликт. Обнаружение конфликта не продвигает baseline, а ждёт явного действия пользователя. Все cloud operations, включая `load`, выполняются последовательно.
7. **Шифрование**: объекты запечатываются заголовком `F95SAVE1` + IV + tag + шифртекст; маркер и каталог тоже. При подключении к существующему зашифрованному хранилищу без фразы состояние `locked`; UI показывает поле «Unlock».
8. **Интеграция в main.js**: контроллер создаётся при регистрации IPC, `start()` после инициализации базы; `scheduleCloudSaveReconcile` идёт в хранилище, если оно готово, иначе ничего не делает; `launch-game` вызывает `watchAfterLaunch(recordId)`; после пробуждения ПК — `scheduleSyncAll("resume")`.
9. **Провайдер `supabase`** (`providers.js`): Storage Object REST без SDK — листинг, чтение, загрузка с upsert и удаление объектов; bucket-admin endpoints и создание bucket не используются. Принимаются только `sb_publishable_…` и legacy `anon` JWT с ролью `anon`; secret/service-role ключи приводят к `unsafe_credentials`. Бакет должен существовать заранее, а Storage policies должны разрешать нужные операции для `anon`. В запросе нет Supabase Auth user token или отдельной user identity. `test()` выполняет пробную запись, чтение и удаление объекта.

## Контракт
IPC: `get-save-storage-state` → `{ state: { connected, type, label, description, encrypted, locked, busy, lastError, lastSyncAt, encryptionEnabled, secretsEncrypted, deviceName, legacyCloudConfigured } }`; `detect-save-storage-folders` → `{ folders: [{ id, label, path, suggestedPath, reason, recommended }] }`; `test-save-storage-connection({ type, fields })` → `{ success, message, existing, encrypted, createdBy }`; `connect-save-storage({ type, fields, passphrase?, encryptNew? })` → `{ success, existing, encrypted, state }` | `{ success: false, needsPassphrase: true }`; `unlock-save-storage({ passphrase })`; `disconnect-save-storage`; `sync-save-storage-all({ mode: "sync" | "upload" })` → `{ summary }`; `sync-save-storage-game({ recordId, action: "upload" | "restore" | "reconcile" })`; `get-save-storage-catalog` → `{ entries: [{ identity, title, creator, threadUrl, engine, updatedAt, fileCount, totalBytes, device, inLibrary, recordId, installed }] }`; `export-save-storage-card({ passphrase? })`; `import-save-storage-card({ filePath?, cardPassphrase? })` → `{ success }` | `{ needsCardPassphrase: true, filePath }`; `forget-save-storage-game({ recordId })`. События: `save-storage-changed` (state), `save-storage-progress` (`{ active, mode, completed, total, currentTitle, summary, source: "storage" }`).

Внутренние поля IPC `fields` (не форма настроек): `folder { folderPath, label }`, `webdav { url, username, password }`, `s3 { endpoint, region, bucket, prefix, accessKeyId, secretAccessKey, forcePathStyle }`, `supabase { url, key, bucket, prefix }` (`key` принимается только для поддерживаемых public-key соединений).

## Граничные случаи и ошибки
- Папка клиента облака недоступна (диск отключён) → ошибки `unavailable` в статусе, локальные функции не затронуты; следующая сверка по расписанию.
- Конфликтные копии клиентов (`latest (conflicted copy).zip`) не читаются приложением; `history/` хранит предыдущие версии для ручного отката.
- Две копии расходятся, а обе стороны считаются изменёнными (в том числе когда baseline-хеши ещё не записаны) → статус `conflict`; mtime не выбирает сторону, baseline сохраняется до явного «Back up» или «Restore».
- Игра из каталога не в библиотеке → показывается как «not in this library yet»; после установки первая сверка её восстановит.
- `safeStorage` недоступен (Linux без keyring) → секреты в открытом JSON, статус предупреждает.
- Неподдерживаемый Supabase key (включая `sb_secret_` и `service_role`) → соединение отклоняется. Для допустимого public key требуется заранее созданный bucket и Storage policies для роли `anon`; пользовательский Auth session приложением не создаётся.

## Проверка
Автотесты: провайдеры (папка, WebDAV с fake fetch включая MKCOL и 401, S3 SigV4 и листинг, Supabase public-key guard), автоопределение, конфиг/секреты/карточки, движок (выгрузка → каталог → восстановление на «втором ПК» → история → сверка «уже синхронизировано», шифрование и блокировка при неверной фразе, ошибки `no_backup`/`no_saves`, сериализация операций и конфликт baseline). Вручную (pending final verification): на двух отдельных ПК/профилях создать baseline, изменить сейвы с обеих сторон, выполнить авто-сверку и убедиться, что конфликт не выбирает сторону по времени; проверить обе явные команды **Back up** и **Restore**; подключить storage A, переключиться на storage B и проверить, что файлы в A остались, а локальные сейвы/vault не изменились; повторить переключение через существующую connection card.
