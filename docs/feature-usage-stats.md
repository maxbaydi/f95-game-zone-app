# Статистика: какие функции используют

**Статус:** active (с версии 1.8.3)
**Модули:** src/main/featureUsage.js (каталог функций, счётчик, `instrumentIpcHandlers`), src/main/usageStats.js (опция `features` у `createUsageStatsReporter`), src/main.js (`featureUsage`, IPC `track-feature`, `app.launch`, сброс на диск), src/renderer.js (`trackFeature`), src/App.jsx (разделы, панель загрузок), src/core/settings/SettingsPanel.jsx (страницы настроек), src/core/settings/GeneralSettings.jsx и src/core/onboarding/OnboardingWizard.jsx (текст о том, что отправляется), stats-worker/src/features.js (подписи, проверка), stats-worker/src/stats.js (`feature_daily`, `features` в `/v1/stats`), stats-worker/src/dashboard.js (таблица «Что используют», вход по ссылке), stats-worker/schema.sql, scripts/usage-stats.js
**Тесты:** test/featureUsage.test.js, test/usageStatsWorker.test.js (вход по ссылке); `node --test test/featureUsage.test.js test/usageStatsWorker.test.js`

## Назначение
Показать разработчику, какими частями приложения реально пользуются, а какими нет, чтобы решать, что развивать, а что упрощать. Это дополнение к счётчику активных пользователей (`usage-stats.md`): к тому же ежедневному анонимному пингу добавляются числа «сколько раз использована функция X».

## Для пользователя
Отдельной настройки нет: учёт работает вместе с **Settings → General → Usage statistics → Send anonymous usage statistics** и выключается тем же переключателем. Выключили — счётчики больше не ведутся, а ещё не отправленные удаляются.

Что уходит: только названия функций из фиксированного списка и числа, например «запуск игры — 14 раз», «синхронизация сохранений — 2 раза». Названий игр, путей, файлов, поисковых запросов и аккаунтов там нет.

## Как это работает
1. **Действия** считаются в main. `instrumentIpcHandlers(ipcMain, featureUsage)` вызывается до регистрации любых обработчиков и оборачивает `ipcMain.handle` только для каналов из `CHANNEL_FEATURES` (например, `launch-game` → `library.launch`, `sync-save-storage-*` → `saves.sync`). Чтения (`get-*`) и вызовы, которые приложение делает само, в список не входят. У `scan-library` автоматический прогон при запуске (`reason: "startup"`) не считается. Счёт идёт до вызова обработчика, исключение счётчика глотается, результат и ошибки обработчика проходят без изменений.
2. **Куда заходят** — сообщает renderer через `window.electronAPI.trackFeature(name)` → IPC `track-feature`; main принимает только имена из `RENDERER_FEATURES`: разделы (`section.library|updates|search|settings`), панель загрузок (`downloads.open-panel`), страницы настроек (`settings.page-*`). `app.launch` main отмечает сам при каждом запуске.
3. Счётчик (`createFeatureUsageCounter`) держит числа в памяти, ограничивает каждое `MAX_FEATURE_USES` (100 000) и раз в час (перед попыткой пинга) и при выходе сохраняет их в `<data>/feature-usage.json`. Считает только когда пинг активен (`usageStatsReporter.isActive()`: есть адрес и переключатель включён), иначе ничего не пишет и удаляет файл. Dev-запуск без `F95LAUNCHER_USAGE_STATS_URL` ничего не считает.
4. Ежедневный пинг (`usageStats.js`) кладёт текущие числа в поле `features`. После ответа 2xx вычитается ровно отправленное; то, что накопилось во время запроса, остаётся до следующего раза. Неудачный пинг ничего не теряет.
5. Worker (`parseFeatures`) принимает до 64 записей вида `группа.функция` с целыми 1…100 000, остальные молча отбрасывает (пинг при этом засчитывается). Числа складываются в `feature_daily` по (день, функция, установка). Неизвестные, но корректные имена принимаются: новая версия приложения может прислать новую функцию раньше, чем дашборд узнает её подпись.
6. `/v1/stats` отдаёт `features` за выбранный период: для каждой функции число разных установок и сумма использований, по убыванию пользователей, затем использований; `reporting` — сколько установок вообще прислали данные о функциях (база для доли).
7. Дашборд, блок «Что используют»: функция, раздел, пользователи, доля от `reporting`, сколько раз, раз на пользователя; ниже — функции из каталога, которыми за период не пользовался никто. Подписи и группы — `stats-worker/src/features.js`, тест сверяет их со списком приложения.
8. Вход в дашборд по личной ссылке `https://<worker>/#key=<STATS_TOKEN>`: страница берёт ключ из фрагмента (на сервер он не уходит), сохраняет в этом браузере и убирает из адресной строки. Кнопка «Скопировать ссылку для входа» даёт такую ссылку для другого устройства. Две функции страницы (`readKeyFromHash`, `buildFeatureRows`) экспортируются для тестов и встраиваются в страницу через `toString()`, поэтому в `wrangler.toml` стоит `keep_names = false` (иначе esbuild добавит в них `__name`, которого на странице нет).

Почему счёт по IPC, а не вызовами в каждом обработчике: один белый список в одном месте, обработчики не меняются, новый канал не попадёт в статистику без явного решения.

## Контракт
- Пинг: `features` — объект `{ "<группа>.<функция>": <целое 1…100000> }`, необязателен (версии до 1.8.3 его не шлют). Имя: `^[a-z][a-z0-9]*(-[a-z0-9]+)*\.[a-z0-9]+(-[a-z0-9]+)*$`, до 64 символов, до 64 записей. Лимит тела пинга — 4 КБ.
- Таблица `feature_daily(day, feature, id, uses)`, ключ `(day, feature, id)`; чистится cron'ом вместе с `daily_active` (400 дней).
- `/v1/stats` → `features: { reporting, items: [{ name, users, uses }] }` (до 100 строк) за окно `days`.
- Файл `<data>/feature-usage.json` = `{ "counts": { "<функция>": <число> } }`; удаляется, когда отправлять нечего или статистика выключена.
- IPC `track-feature` (invoke, ответа нет), `window.electronAPI.trackFeature(name)`.
- Группы: `app`, `section`, `library`, `import`, `catalog`, `downloads`, `updates`, `saves`, `settings`. Новая функция: строка в `CHANNEL_FEATURES` или `RENDERER_FEATURES` + подпись в `stats-worker/src/features.js` (иначе упадёт тест каталога).
- `npm run stats` печатает таблицу функций (сырые имена, пользователи, доля, раз).

## Граничные случаи и ошибки
- Пользователь открыл приложение один раз: пинг через 90 с уносит то, что успел; остальное уйдёт при следующем запуске. Счёт попадает на день отправки, а не на день использования.
- Приложение упало: теряется не больше часа счёта (файл пишется раз в час и при выходе).
- Файл повреждён или содержит чужие имена/числа — читается только корректное, остальное отбрасывается.
- Старые версии без поля `features` учитываются в активных пользователях, но не в доле функций; пока никто не обновился, блок пишет, что данных нет.
- Пользователь на 7-дневном окне, который не запускал приложение заново (живёт в трее), может не попасть в `reporting`, если за окно ничего не делал.
- Поддельные пинги могут прислать выдуманные имена — они видны в таблице как есть, на другие данные не влияют.

## Проверка
- Автотесты `test/featureUsage.test.js`: белый список и каналы (включая автоскан при запуске), обёртка IPC (результат, ошибки, сломанный счётчик), выключенная статистика, файл после перезапуска и мусор в нём, пинг с `features` и вычет отправленного, разбор на worker'е, сложение по дням, `reporting`, очистка, таблица дашборда, `npm run stats`, совпадение каталога с подписями. `test/usageStatsWorker.test.js`: разбор `#key=` и `keep_names = false`.
- Вручную:
  1. `cd stats-worker`, `.dev.vars` со строкой `STATS_TOKEN=local-test-token`, `npx wrangler d1 execute f95launcher-stats --local --file=schema.sql`, `npx wrangler dev`.
  2. В корне: `$env:F95LAUNCHER_USAGE_STATS_URL = "http://localhost:8787"`, `npx electron . --user-data-dir=<временная папка>`; через 90 с появится пинг с `app.launch` и `section.library`.
  3. Открыть `http://localhost:8787/#key=local-test-token` — дашборд открывается без ввода, ключ исчезает из адреса, блок «Что используют» заполнен.
